Audit report and build plan · GoStyle backend

Rating & Review Service

Build the rating and review service by moving the existing review code out of gostyle-platform, not by starting from scratch. Give it the push-notification-service layout and its own Postgres, and use Prisma 7 the way gostyle-booking-api does.

Prepared by Imran Khan Rafa As of 8 Oct 2026 Read only: no code changed, nothing run against a database

Recommendation

  • Extract, don't duplicate. Reviews already exist in packages/nest-storefront: four tables, single-use invite links, salon replies, reports and HQ moderation. A second review system next to it would split one salon's reputation in two.
  • One owner, one database. Only review-service holds review data, in review-db. No other service reads its tables, including customer-api, which does today.
  • Keep the anti-fraud model. One review per completed booking, written only with a single-use invite token. Port the platform's rules unchanged.
  • Store the rating summary. Keep each storefront's average and counts in a summary table updated in the same transaction as each review. Recompute it nightly, and send it to customer-api as events.
  • Outbox for every event. Save events in the same transaction as the data. The push service's "save, then queue" order can lose work when Redis is down.

Seven decisions need an answer before Phase 1 starts (section 9). The biggest is whether stylists get their own rating.

Gaps found

Gap Mobile bookings get no invite

gostyle-booking-api keeps bookings in its own database. Its events run through in-process listeners and end in LoggingEventPublisher, so nothing reaches the platform's invite listener.

Gap Stylists can't be rated

No review links to a staff member. customer-api's expert_profile.py returns rating: null and review_count: 0 for every stylist.

Gap No in-app review

The WhatsApp link is the only way to write a review. A customer who is logged in to the app can't review from there.

Gap Shared-database coupling

customer-api's SQL reads storefront_review directly. Those queries break as soon as the tables move.

Check No path to REMOVED

The REMOVED state exists, but I found no code that sets it or brings a HIDDEN review back.

Check A second rating source

customer-api's own Salon model has static rating and reviews columns, separate from the real reviews.

Database

The service owns one Postgres database, review on review-db, changed only through Prisma migrations. Other services never connect to it.

TablePurposeKey constraints
reviewOne row per reviewUUID v7 id. UNIQUE (booking_source, booking_id). CHECK rating 1–5. Index (storefront_id, state, created_at).
review_replyThe salon's answerUNIQUE review_id; foreign key with cascade; hard delete.
review_inviteThe only way to writeUNIQUE (booking_source, booking_id). UNIQUE token_hash. Index on expires_at.
review_reportComplaints about a reviewPartial UNIQUE (review_id) WHERE status = 'OPEN'. Index (status, created_at) for the HQ queue.
rating_summaryRead modelPrimary key (subject_type, subject_id). Count, rating sum, five histogram columns, two language columns. Average = sum ÷ count, rounded at read.
review_staff_ratingPer-stylist stars (later)Primary key (review_id, staff_id). CHECK rating 1–5.
outbox_eventEvents waiting to leaveSame shape as booking-api's event_outbox, with an index on unpublished rows by created_at.
inbox_eventEvents already handledPrimary key (source, event_id), so every consumer can safely see an event twice.

Changes from today's tables

  • booking_source joins the unique keys. Two booking systems now mint booking ids, and the key should say which system an id belongs to.
  • A CHECK on rating. The platform left it out so error messages come from the domain. The domain still writes the message; the CHECK is a backstop in a database no other code shares.
  • The summary is stored. The platform refused to store it because a stored average drifts. Across a service boundary customer-api can't run the query, so the drift risk is handled instead: same-transaction updates plus a nightly recompute.

Prisma conventions

  • prisma.config.ts holds the URL and migrations path. The generator writes to src/generated/prisma with moduleFormat = "cjs", as booking-api does.
  • One PrismaService using @prisma/adapter-pg, shared by every repository.
  • snake_case @@map, @db.Uuid, @db.Timestamptz. Enum types get a suffix (review_state), because Postgres types and tables share one namespace.
  • Partial indexes and CHECKs are hand-written into migration.sql, made safe to re-run with IF NOT EXISTS.
  • prisma migrate deploy runs as its own step before the app starts, never inside the app at boot.
  • tenant_id on every row. No foreign keys to other services' ids (storefront, branch, booking, customer, staff).

Handler rules

  • Write side. Load the aggregate, call its method, then save it and its events in one $transaction. Return the id.
  • Read side. Query handlers read Prisma straight into response DTOs and skip the aggregate. The push service's GetNotificationHandler loads the aggregate; that's fine for one row but slow for lists.
  • Errors. Domain errors carry a code (INVITE_EXPIRED → 410, INVITE_ALREADY_USED → 409, VALIDATION_FAILED → 422), mapped in one place.
  • Tenant. Public routes take the tenant only from the invite row. Console routes take it only from the JWT. Never fall back to a default tenant (the platform's @TenantId() does, and its own code warns about it).
06

How it connects to other services

Other services reach reviews only through events and HTTP, never through the tables.

  • Events in. A consumer for booking.completed from both booking systems. It records each event id in inbox_event first, so a redelivery does nothing.
  • Events out. The outbox relay delivers to each consumer over HTTP with a per-caller key. The receiver dedupes by event id. booking-api already calls the push service this way.
  • Push. When a salon replies, call POST /notifications/user with eventId = review:<id>:reply. The push service drops repeats of the same eventId.
  • The token never travels. The plain token exists only between minting and the WhatsApp send. Events carry the invite id, and logs carry the booking id.
  • Auth. Staff send the platform JWT (issuer gostyle-api), checked the way booking-api's token-verifier.service.ts does. HQ routes also check storefront.review_moderation.

08

Build plan

Eight phases in four stages, with a gate between stages. Durations are left out until the decisions in section 9 set the scope.

P0

Decide and agree the contract

  • Answer the seven decisions in section 9.
  • Write the OpenAPI contract for every endpoint in section 5, keeping today's console paths.
  • Agree event names and payloads with the booking-api and platform owners.
  • Count today's review, invite, reply and report rows. The count sets the backfill effort.

Done when the decisions are written down and the console FE, customer-api and platform owners have reviewed the contract.

P1

Skeleton

  • New repo review-service in the push-service layout: Yarn 4, Node 22, NestJS 12, Vitest, oxlint.
  • Prisma 7: prisma.config.ts, the cjs generator, @prisma/adapter-pg, one PrismaService.
  • Validated config, /health (DB and Redis), pino JSON logs, request id, one error filter.
  • Docker: multi-stage image; Compose with review-db and review-redis on gostyle-net; prisma migrate deploy as a step before the app starts.
  • CI: typecheck, lint, unit tests, and a check that the schema and migrations agree.

Done when an empty service deploys, /health is green, and the first migration applies to a fresh database.

P2

Domain

  • Port review-rules.ts, review-invite-rules.ts and computeAggregate() with their specs, unchanged.
  • Build the Review (with Reply), ReviewInvite and ReviewReport aggregates: private constructor, create(), restore().
  • Value objects from section 3, and a coded DomainError for every rule.

Done when the domain specs pass and domain/ imports no Nest module other than @nestjs/cqrs, and no Prisma or database code.

P3

Write side

  • Prisma models and the first migration, with the hand-written CHECK and partial unique index.
  • Repositories behind ports; every write method takes an optional tx.
  • The command handlers from section 5, each saving data and events in one $transaction.
  • Outbox relay as a BullMQ repeatable job; inbox_event for consumed events.
  • DB specs on a real Postgres, plus scripts/proof.sql with inserts that must fail.

Done when every rule in section 3 has a spec or a must-fail proof, and each proof fails the way it should.

P4

Read side

  • rating_summary projector, running in the same transaction as the review change.
  • Nightly recompute that logs and repairs any difference.
  • Query handlers, then the public, console, moderation and internal controllers, with Swagger and throttling on public routes.

Done when stored summaries equal a full recompute on seeded data, and every endpoint passes its contract test.

P5

Connect

  • Consume bookings.booking.completed.v1 from gostyle-platform.
  • In booking-api, forward booking.completed out of its outbox. Today the publisher chain ends in LoggingEventPublisher.
  • Move the WhatsApp invite sender and the contact lookup behind ports in review-service.
  • Push "the salon replied" through POST /notifications/user.
  • In customer-api, add a local rating table fed by rating.summary.changed.v1, and switch discoverable_salons() and the map pins to it.

Done when a completed booking in either system produces exactly one invite, and customer-api shows ratings without reading storefront_review.

P6

Migrate and cut over

  • Backfill: copy the four platform tables into review-db with the same ids, then build the summaries.
  • Shadow mode: the platform keeps serving while review-service gets the same events. A compare job checks counts and averages per storefront.
  • Switch reads (console, public, customer-api) to review-service.
  • Switch writes in one deploy: platform listener and routes off, review-service consumer on. Freeze writes briefly to copy the last changes.

Done when the shadow compare stays clean for the agreed period and all review traffic reaches review-service.

P7

Clean up and harden

  • Remove review code from nest-storefront, the gostyle-api controllers, and customer-api's StorefrontReview model.
  • Back up, then drop the four platform tables in a platform migration.
  • Cleanup job for expired unused invites and closed reports past retention.
  • Dashboards: outbox lag, invites minted vs redeemed, age of the oldest open report.

Done when no code outside review-service touches review tables.

Later

Close the remaining gaps

  • Stylist ratings: review_staff_rating, a stylist summary, and customer-api's expert profile reading it.
  • In-app reviews for logged-in customers, still redeeming the booking's invite row.
09

Decisions, open questions and risks

Decisions for the team

#DecisionOptionsRecommendation
1Extract today's reviews, or build a new service beside them?Extract / build new scope onlyExtract. Building beside them gives one salon two ratings.
2What can be rated?Salon only / salon + stylist / + each serviceSalon now; stylist later, as extra stars on the same review. That keeps one review per booking.
3How do events cross services?HTTP from each outbox relay / shared Redis streams / a message brokerHTTP from the relay, signed with a per-caller key and deduped by event id. Revisit a broker when a third consumer appears.
4Who sends the invite message?review-service / the platform keeps sendingreview-service. The plain token exists only at mint time, and only there.
5In-app reviews for logged-in users?Link only / app as wellApp as well, after launch. It still redeems the invite row. Needs the identity mapping below.
6Stored or computed rating?Compute on every read (today) / stored summaryStored summary with a nightly recompute. customer-api can't run the query across services.
7Do consoles call review-service directly, or through gostyle-api?Direct with the platform JWT / proxy in gostyle-apiDirect. booking-api already checks platform JWTs, so the pattern exists.

Open questions

  • How does a customer-api account map to a platform customer_id? The platform gives the same person a different customer_id at each salon. In-app reviews and reply pushes need this mapping.
  • After the move, who answers the contact lookup (name and phone): a platform internal API or customer-api?
  • Are reviews live in production, and how many rows exist?
  • Are mobile bookings copied into the platform anywhere? I found no such path in the code.
  • Does anything still read customer-api's Salon.rating and Salon.reviews columns?
  • Should HQ get hide, restore and remove actions? No code sets REMOVED today.
  • How long do expired invites, closed reports and REMOVED reviews stay?
